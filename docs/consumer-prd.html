预约 7 步流程详解
步骤内容关键逻辑
Step 1选择设备品牌展示已激活的维修服务品牌列表
Step 2选择设备型号按品牌过滤服务目录中的型号
Step 3选择维修类型该门店对应型号的可用服务（屏幕更换、电池更换等）
Step 4选择日期未来 7 天可选，已满 / 休息日灰化
Step 5选择时间槽30 分钟间隔，根据 MerchantHours 动态生成，排除已有预约
Step 6填写联系信息姓名 + 手机号预填（如已登录），可编辑
Step 7确认 & 提交显示汇总，提交创建 RepairBooking，触发 SMS
时间槽生成算法

服务端生成，不由客户端计算。

输入：merchantId, serviceId（影响服务时长）, date

1. 查 MerchantHours → 获取当日 openTime / closeTime / isClosed
2. 如果 isClosed → 返回空数组
3. 生成 30 分钟间隔 slots：[09:00, 09:30, 10:00 ...]
4. 查 RepairBooking → 获取当日已确认预约的时间
5. 排除与现有预约冲突的 slots（考虑服务时长 overlap）
6. 排除过去时间（今天的话）
7. 返回可用 slot 列表

OTP 存储：Redis，Key = otp:{phone}，Value = 6 位数字，TTL = 5 分钟。
新用户自动注册（手机号即身份），首次登录创建 User 记录。
登录后写 user_token HttpOnly Cookie（7 天有效）。

五、数据模型变更

Consumer 端需要在现有 Prisma schema 基础上新增和修改以下模型。

关键缺口：当前 schema 无 User 模型，无法存储消费者身份。RepairBooking 的 userId 字段为 nullable，新建预约时必须关联 User。
新增：User 模型
id Int @id 主键
phone String @unique 手机号，爱尔兰格式 +353xxxxxxxx，登录唯一标识
name String? 用户姓名（首次登录可选填，预约时必填）
email String? 邮箱（OAuth 登录后填充）
isActive Boolean 账号状态，默认 true
createdAt DateTime 注册时间
bookings RepairBooking[] 关联预约
修改：RepairBooking 模型
userId Int? 关联 User（现有字段，待填充；生产环境应改为必填）
user User? 新增关联 @relation(fields: [userId], references: [id])
新增：SmsLog 模型（OTP 追踪 + 审计）
id Int @id
phone String 接收手机号
type SmsType 枚举：OTP_LOGIN / BOOKING_CONFIRM / BOOKING_CANCEL / BOOKING_COMPLETE
status String sent / failed / delivered
twilioSid String? Twilio Message SID，用于追踪状态
createdAt DateTime

六、API 规格

Consumer 端所需的全部新增 API 端点。按鉴权要求分三类。

A. 公开 API（无需登录）

方法路由说明关键参数
GET /api/public/stores 按 Eircode 搜索附近门店 eircode, radius=5, limit=20, offset=0
GET /api/public/stores/{id} 门店详情（信息 + 营业时间） —
GET /api/public/stores/{id}/services 门店激活的维修服务列表 —
GET /api/public/stores/{id}/products 门店在售商品列表 limit, offset
GET /api/public/stores/{id}/slots 门店某日可用时间槽 date (YYYY-MM-DD), serviceId
GET /api/public/products/{id} 商品详情 —
GET /api/public/categories 品类列表（首页导航用） —
Eircode 搜索实现流程：
1. 验证 Eircode 格式（正则 /^[A-Z0-9]{3}\s?[A-Z0-9]{4}$/i）
2. 查 Redis：GET geo:{eircode}，命中则直接用缓存坐标
3. 未命中：调 Google Maps Geocoding API，写 Redis（SET ... EX 2592000，30 天 TTL）
4. 执行 Prisma raw SQL：SELECT ... FROM merchants WHERE ST_DWithin(location, ST_MakePoint($1,$2), $3)

B. 用户认证 API

方法路由说明请求体 / 响应
POST /api/auth/otp/send 发送 OTP 到手机 body: {phone} → 200 {expires: 60}
POST /api/auth/otp/verify 验证 OTP，登录/注册 body: {phone, code} → 设置 Cookie，返回 {user}
POST /api/auth/logout 退出登录 清除 user_token Cookie
GET /api/auth/me 当前用户信息 需要 Cookie → {id, name, phone}

C. 用户鉴权 API（需携带 user_token Cookie）

方法路由说明关键参数
POST /api/user/bookings 创建预约 body: {storeId, serviceId, date, slot, name, phone, notes}
GET /api/user/bookings 我的预约列表 status, limit, offset
GET /api/user/bookings/{id} 预约详情 —
PATCH /api/user/bookings/{id} 取消预约（P2） body: {action: "cancel", reason}
PATCH /api/user/profile 更新用户信息 body: {name, email}

预约创建时的副作用

POST /api/user/bookings 成功后，服务端同步触发：

1. 创建 RepairBooking 记录（status: "pending_confirm"）
2. 向用户手机发送 SMS（Twilio）：
   "Your repair booking at {storeName} on {date} {time} has been received.
   Booking ref: #{id}. We'll confirm shortly."
3. 记录 SmsLog
4. （可选）触发商家侧通知（商家在 merchant portal 看到 pending count 变化）

九、关键 UX 决策汇总

决策点选择原因
登录时机 游客可浏览，点「预约」时拦截 降低浏览门槛，提高转化；爱尔兰用户不愿意"先注册再看"
登录方式 MVP 仅手机 OTP（Twilio） 简单可靠；爱尔兰手机普及率 100%；不依赖 Google 账号
Eircode 持久化 localStorage，刷新保留 爱尔兰用户一般只在一个地区使用；避免重复输入
预约流程 同一页面 Step Wizard，不换 URL Mobile 体验更流畅；刷新重置符合预期（防止脏数据）
时间槽生成位置 纯服务端生成 避免客户端时区问题；业务规则统一管理
手机号格式 +353 统一存储（E.164 格式） Twilio 要求 E.164；避免前端存格式不一致
预约唯一性 服务端检查同一门店同一时槽 客户端选槽与服务端提交有时差，必须服务端二次校验
