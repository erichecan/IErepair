待补充功能

以下功能缺失是 B2B2C 商业模式无法运转的直接原因，按优先级排列。

优先级 缺失功能 阻塞原因 B2B2C 影响 前置依赖
P0 门店选品管理视图
Admin 查看各门店已选商品、定价、上下架状态
 无 MerchantProduct 表，无从查看 Admin 对平台在售商品完全盲视 需先建 MerchantProduct Schema
P0 维修预约总览
跨门店预约列表、状态筛选、快速跳转门店详情
 无 RepairBooking 表 Admin 对核心交易数据完全不可见 需先建 RepairBooking Schema
P0 门店营业时间管理
在门店详情页配置每天营业时间段，供消费者预约时选择
 无 MerchantHours 表 用户无法知道门店何时开门，预约系统无法运转 需先建 MerchantHours Schema
P1 商品审核流程
Admin 审核商家申请入库的自定义商品，通过/拒绝
 现商品只有 status: active/inactive，无 pending/rejected 状态 平台内容质量失控，恶意商品无法拦截 Product.status 扩展 + 审核 UI
P1 Admin 账号管理
后台 CRUD 管理员账号，角色分配（超管/运营/只读）
 现只能直接操作数据库新增 AdminUser 多人运营时无法分权，离职账号无法在 UI 停用 AdminUser CRUD API + UI
P2 佣金 / 平台收益概览
按时间段统计门店交易额、平台抽佣、已结算/未结算明细
 无订单/支付系统，暂无数据源 B2B2C 核心收益无法量化和追踪 依赖 Stripe Connect 订单数据（Phase 2）

缺失表（阻断交易的根本原因）

MerchantProduct NEW
✗ 缺失
致命缺失 — 门店从母库选品实例：merchantId, productId, price, isActive, stock。商家选品写这张表，消费者搜索商品价格读这张表。无此表，B2B2C 中间层完全缺失。
MerchantService NEW
✗ 缺失
致命缺失 — 门店提供的维修服务实例：merchantId, repairServiceId, price, durationMinutes, isActive。"这家门店换 iPhone 15 屏幕 €89"就是这张表。
MerchantHours NEW
✗ 缺失
门店营业时间：merchantId, dayOfWeek, openTime, closeTime, isClosed。无此表则无法生成可预约时间段。
User NEW
✗ 缺失
消费者账号：phone, name, email, OTP 字段。无消费者账号，所有需要登录的操作（我的预约、收藏）均无法实现。
RepairBooking NEW
✗ 缺失
致命缺失 — 预约主体：userId, merchantId, merchantServiceId, scheduledAt, status, smsLog。整个预约闭环的数据载体。

Merchant / Consumer 端现状

B2B2C 无法运转的直接原因：下游两端完全为零，数据无法流动到消费者。

商家端 Merchant
登录后台 → 浏览商品母库 → 选品上架 + 定价 → 配置营业时间 → 查看接受预约
0% — 完全为零 账号数据已在数据库，但无任何前端页面和 API。详见 merchant-prd.html。
消费者端 Consumer
静态首页 → Eircode 搜索 → 门店商品发现 → 手机号登录 → 维修预约 → 预约管理
5% — 仅静态首页 仅 src/app/page.tsx 静态展示页。详见 consumer-prd.html。

优先级建议

四个阶段，从解锁 Merchant 端开始，逐步打通完整交易闭环。

🔴 P0 — 解锁 Merchant 端（先决条件）

  • 建 MerchantProduct、MerchantService、MerchantHours 表（Prisma migration）
  • Merchant 登录 API + Cookie Session 鉴权
  • /merchant/products/catalog — 浏览母库 + 选品
  • /merchant/products — 已选品列表 + 调价
  • /merchant/settings — 营业时间配置

🟡 P1 — 解锁 Consumer 搜索（核心用户价值）

  • 建 User 表 + 手机号 OTP 登录（Twilio）
  • PostGIS 安装确认 + ST_DWithin 查询 API
  • /search — Eircode + 关键词 → 附近门店商品
  • /products/[id] — 商品详情 + 在售门店价格
  • /stores/[id] — 门店详情页

🔵 P2 — 完成预约闭环（让业务跑通）

  • 建 RepairBooking 表
  • /repair/book — 预约表单（选机型/故障/门店/时段）
  • Merchant 端预约管理（接受/完成）
  • Admin 预约总览
  • Twilio SMS — 预约确认通知

🟢 P3 — Admin 补充功能（锦上添花）

  • Admin 账号管理 UI（角色分权）
  • 商品审核流程（pending/approved/rejected）
  • 门店选品管理视图
  • 佣金概览（依赖 Stripe Connect，Phase 2）
  • Redis 缓存（Upstash）接入

核心判断

⛔ 现阶段 B2B2C 商业模式无法运转
Admin 后台已完成上游内容管理（维修目录、商品母库、门店账号），但缺少 3 张核心关联表（MerchantProduct、MerchantService、MerchantHours），导致"平台定义的内容"和"门店实际在售的商品/服务"之间没有任何桥接。Merchant 端 0% 未建，Consumer 端 5% 仅有静态首页。整个交易主链路：商家选品 → 消费者发现 → 消费者预约 → 门店接单，完全不通。
✅ Admin 后台自身已具备运营能力
管理员可以完整维护维修目录（5 层级联）、管理商品母库（含 CSV 批量导入和 R2 图片上传）、创建和管理门店账号（含 Eircode 自动解析坐标）。这部分工作已经到位，是后续 Merchant 端和 Consumer 端的数据基础。下一步只需专注打通 Merchant 端，即可让第一个商家完成选品，之后便可验证 Consumer 端搜索是否能找到该商家的商品。
